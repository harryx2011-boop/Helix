# Helix — context

> **1.16.2** (2026-09-05): **the Anthropic path stops forcing the model's hand, and a cancel poll that could never fire now can.** Every Anthropic call site (`schema_compiler.py`, `llm.py`, `schema_gen.py`) sends `tool_choice: {"type": "auto"}` instead of forcing tool use — a forced choice returns 400 on newer models, so this was a migration hazard sitting in code nobody had reason to touch. Strict tool schemas (`strict: true` plus the existing `_strictify()` pass) apply to both the tool-based fallback and a new `output_config.format` path used when the installed SDK supports it, gated by `_anthropic_supports_output_format()` rather than a version string. A text-only or invalid-JSON answer on either branch now raises a descriptive `SchemaError` that passes through unretried — a content failure was never supposed to trigger cross-provider fallback, and now says so.

**The audit half: two unbounded awaits that could starve a cancel check.** `provider.py`'s one genuine unbounded await (`await call()`) is now wrapped in `asyncio.wait_for(..., CALL_TIMEOUT_SECONDS)`, translated to a non-retryable `ProviderError` on timeout — the same class of bug 1.16.1 fixed in the crawl worker's `Promise.race(inFlight)`, here in the provider layer instead of the frontier loop. `embeddings.py`'s `_embed_openai` gets the same ceiling; it was the one previously-unbounded SDK call with no timeout of its own. On the API side, `controller.signal` now threads into the extract and parse route call sites that `document.ts` and the sibling routes had already established the convention for (`extract.ts:177`, `parse.ts:239,269,540`), and `document.ts` gets its own `AbortController`/`abortable()` pairing reporting `reason:'aborted'` the same way.

Verified: **apps/extract** 265 passed / 20 skipped (up from 251 at 1.16.0/a9e9003 — new coverage for the auto-choice and output-format branches); **apps/api** 85 files / 1263 passed; `tsc` clean. No response contract changed — `compile_anthropic`'s return shape is unchanged, `compile_anthropic_output_format` is a pure addition, and the tool-choice change is an internal detail of `_call_anthropic`/`_call_anthropic_json` no caller of `extract_structured` or `generate_schema` observes except via a more descriptive `SchemaError` message.

> **1.16.1** (2026-09-05): **cancelling a crawl now stops the work it was paying for.** `DELETE /v1/crawl/{id}` marked the job cancelled and the frontier stopped handing out pages, but anything already in flight ran to completion — including the per-page `extractClient.structured()` call added in 1.14.0, which bills the caller's own provider. A job-scoped `AbortController` is aborted when the cancellation poll sees the flip (and on worker shutdown), and its signal now reaches both the pipeline fetch and the structured call.

**Three things had to be true for that signal to be worth having, and only the first was obvious.** An abort must not be *counted* as a failure: the catch around structured extraction incremented `jsonFailed` and logged a warning, so a cancelled crawl would have reported dozens of pages the extractor "tried and lost", and any retry layer reading that count would re-fire the call the cancellation had just killed. A page the pipeline reports as `aborted` must not be written to `fetch_failures` either — but only when the job itself caused it, because an `aborted` from anywhere else still has to reach the frontier or the row stays leased and `pending` never drains, which is a spin until the lease expires. The cancelled case is deliberately left leased: `frontier.release()` runs immediately afterwards and returns it to `queued`, so a resumed job retries the page rather than skipping it as done or spending an attempt on it.

**The bug underneath was that the poll could not fire at all.** With one slow page outstanding and nothing queued, the loop blocked on `await Promise.race(inFlight)`, which resolves only when that page finishes — so a crawl whose last page took two minutes could not notice it had been cancelled for two minutes. The signal existed and nothing reached the check that fires it. `raceInFlight()` now races the in-flight set against a timer bounded by the poll interval, so the check is never more than `CANCEL_POLL_MS` away. Found by a test that kept a page outstanding for 2.5 seconds; it passed at 60ms for the wrong reason before that.

> **1.16.0** (2026-09-05): **structured extraction gets a fallback chain, a price tag, and an abort that actually reaches the model call — and the clip notice gets proven, not just claimed.** `call_structured` now retries a transport-class failure (auth, rate limit, timeout — never a content or schema error, which re-raises immediately) against the next provider a caller has usable credentials for, in a fixed preference order (anthropic, then openai, then gemini, then openrouter), never crossing a provider's own key into another provider's call. `ExtractionResult` reports `provider_used` and `fallback_from` so a caller can see whether the answer came from the provider they asked for or a substitute, and every response now carries `cost_usd` from a new `pricing.py` — a pinned per-(provider, model) rate table, cache-read and cache-write priced as multipliers of the same fresh-input rate the way every provider that reports cache tokens actually publishes it, `None` for a model this table has no cited source for (not a guessed `0.0`), and a real `0.0` for a local runtime (Ollama, vLLM, an OpenAI-compatible endpoint) because that genuinely costs nothing. The API's own abort controller — already wired to the caller's disconnect — now reaches `extractClient.structured()` and `.document()` the same way it already reached `.schema()`, so a caller who hangs up mid-`/parse` stops the extract-side model call instead of it running to completion unread.

**The clip notice was already per-page; this release adds the test that proves it, and a `finally` a route was missing.** `relevance.select()`'s clip notice fires once per `extract_structured` invocation against one page's content string — there was no aggregate path to feed it a cross-page count, and a new test drives that directly rather than leaving it an inference from reading the call graph. Separately, `parse.ts`'s abort listener is now wrapped in the same `try/finally` every other route in this pass already used (`agent.ts`, `extract.ts`) — without it, a route with nine early-return paths leaked the `onClose` closure on each one; harmless on a resolved controller, but the one place this diff's own pattern wasn't applied consistently.

Verified: **apps/extract** 251 passed / 20 skipped; **apps/api** 1256/1256 (the one full-suite failure in `pool.test.ts` is the documented flake under parallel real-browser launches — 16/16 passing in isolation, not a regression), `tsc` clean.

> **1.15.0** (2026-09-05): **the Converter records your screen, and two options that were declared but ignored now do something.** `apps/converter/app/record` captures a window, a tab or the whole screen for up to 30 minutes, with an optional microphone track mixed in through Web Audio, then hands the result to the ffmpeg worker the rest of the app already uses — so a WebM capture becomes an MP4 or a GIF without a second encoder. Everything stays in the tab: the capture, the encoding, the storage, and the only byte that leaves is a file the user saves to their own disk.

**Recordings live in IndexedDB, not localStorage, and that is not a style choice.** localStorage holds strings in roughly 5 MB per origin; a 30-minute capture is 300 MB to 2 GB of binary, so a recording written there throws `QuotaExceededError` within seconds. IndexedDB stores Blobs natively, is bounded by disk rather than a fixed cap, and — unlike the blob URLs the converter uses elsewhere — survives a reload, which matters for something a person spent half an hour making. Chunks are written **as they arrive**, one per second, rather than accumulated in an array and saved at the end: a crash at minute 29 costs one second, not 29 minutes. A row left mid-write by a closed tab is pruned before the list renders, because presenting a partial capture as a finished one is worse than not offering it — the user cannot tell which minutes are missing. VP9 is used here despite 1.12.0 taking WebM off the table for conversion: that hang was `libvpx-vp9` inside `@ffmpeg/core`, and this is the browser's own `MediaRecorder`, a different encoder entirely.

**Two bugs that only a real browser could find.** The trim handles could be pushed until they *met* — `end - 0.1` rounds back to `end` at a tenth-second step, giving ffmpeg a zero-length range it accepts and answers with an empty file; the clamp now rounds to the step and the export refuses a selection below it. And the export's blob URL was revoked the instant it was created: the cleanup effect had `result` in its dependency array, so setting the result re-ran the effect and the *previous* cleanup released the URL the Save link had just been given. The URL is held in a ref and released on unmount only. Both were found by driving the page with a real Chromium and reading the exported bytes — the MP4 begins `ftypisom` and the GIF `GIF89a`, which is the check that distinguishes a working export from a plausible-looking failure.

**`ImageOptions.fit` was declared, validated, and then ignored.** The image worker hardcoded jSquash's `fitMethod: 'stretch'`, so `cover`, `contain`, `inside` and `outside` all produced the same stretched output. jSquash offers only `stretch` and `contain`, so the other three are computed before the resize now, with `cover` doing a real centre crop rather than letterboxing. A new `thumbs` op joins the engine union: a poster frame at a timestamp, a contact-sheet sprite whose frames are spaced across the whole clip, or an animated WebP preview. A sprite wider than 16,384px is rejected at the validator rather than failing late in wasm.

> **1.14.0** (2026-09-05): **the three products catalogued in 1.13.0 become callable, and Crawl learns to return a table.** `POST /v1/document` dispatches by `op` to parse, convert, metadata, scrub and assess — it forwards rather than reimplements, re-entering the router at each operation's own path, because those routes own multipart parsing, body limits, in-flight caps and result caches that a second copy would drift from. The four original paths stay registered and unchanged. `POST /v1/extract` applies one schema across up to 25 URLs and returns rows; `/v1/screenshot` gains `fullPage`, `selector`, `clip`, `format`, `quality`, `omitBackground`, `viewport` (with `dpr`), `darkMode` and `blockAds`.

**The crawl work was half-built already, and the scope shrank when the code was read rather than remembered.** Four of the seven planned additions existed under other names — `discovery` was `sitemap: include|skip|only`, `concurrency` was `maxConcurrency`, `changesOnly` was `incremental`, and the estimate had been implemented all along behind `estimate: true`. **Neither planned migration was needed**: `crawl_state` has carried `content_hash`, `etag`, `last_modified` and `unchanged_streak` since 001, the worker already skipped unchanged pages via `isUnchanged()`, and `PersistentFrontier` already rebuilt from `job_tasks` after a crash. What was genuinely missing and now exists: content-level `includeContent`/`excludeContent` filters (path patterns cannot express "skip the login wall" when every such page has a distinct URL), a `maxPagesPerPath` budget that bounds calendar and facet traps, `resume` for a job the *caller* cancelled (the frontier survives; un-cancelling did not), `POST /crawl/estimate` as its own route, and site-wide `scrapeOptions.jsonOptions` — the addition that turns a crawl into a dataset builder rather than 500 markdown blobs.

**Three things are now said out loud that were previously inferable only by counting.** A crawl reports `pagesFiltered`, `pagesOverPathCap`, `jsonExtracted` and `jsonFailed` in `usage`, so a short result is explicable rather than mysterious. Every extracted page carries `blocksKept`/`blocksTotal` in its metadata, because a page whose blocks were clipped answered from part of itself and the value alone cannot show that. And `/v1/extract` **drops** a field with no grounding span in its source, reporting it in `dropped[]` rather than returning a plausible number nobody can check — the post-hoc-discard half of `prompt-assembly.md` rule 8, whose other half is the structural `<untrusted origin=…>` fence helix-extract now puts around page content (terminator defanged), which also tells the model when relevance ranking clipped blocks. A `formats: ["json"]` crawl with no schema or prompt is now a 400 rather than a silently dropped field on every page.

**A shared request blocker turned into one handler.** Ad and consent-dialog blocking could not be a second `context.route` — Playwright runs handlers most-recently-registered first and stops at the one that answers, so two handlers each calling `continue()` would race, and the private-host guard could be bypassed by whichever registered later. `blockRequests` now decides both in one place. The dashboard's health page (built by another session directly on this catalog) states each endpoint's hard and soft dependencies; `screenshot` deliberately omits `extract`, which is in its `Deps` but never called because the route passes `skipExtraction: true`.

> **1.13.0** (2026-09-05): **three endpoints that already existed become three products, and four collapse into one.** Screenshot and structured extraction were shipped code with no name — `POST /v1/screenshot` has been live since the pipeline gained a Chromium tier, and structured extraction has been reachable as `scrapeOptions.jsonOptions.schema` plus `/v1/agent/schema` — but neither appeared in `lib/catalog.ts` as a product, so neither had a page, a nav row, or a name anyone could ask for. Both are now catalogued. Going the other way, Parse, Convert, Metadata and Assess stop being four things a caller has to know about separately and become four operations of one **Document API**; the four routes are untouched and keep working, and `/parse` and `/metadata` still render (as the Document page, canonical to `/document`) rather than redirecting, because `output: export` does not run `redirects()` and a rewrite would 404 the self-host build.

**The nav is now derived from the catalog rather than hand-listed.** `API_GROUPS` maps `TAB_GROUPS` over `PRODUCTS`, so the menu grows a row when an endpoint's `product` flag flips and never again drifts from the catalog by hand. Capabilities → **APIs**, Utilities → **Tools**; Status moves into Tools instead of sitting as a bare top-level link, and the Converter gains sub-rows (Convert · Compress · Record) where it previously hid behind a single external link.

**A `runnable` flag stops the catalog promising tabs the playground does not have.** Document, Extract and Screenshot are catalogued and documented ahead of their SDK methods, and four separate surfaces would each have rendered a dead `/app/playground?tab=…` link for them — the capability-page CTA, the docs-page CTA, the app sidebar, and the overview grid. `RunnableEndpoint` (`Exclude<Endpoint, 'document' | 'extract' | 'screenshot'>`) plus `RUNNABLE`/`runnableById` make that a compile error rather than a 404: the playground's own maps key off the narrow type, and `orderBySelection` returns only runnable entries. Two further gaps found the same way — `/docs/document`, `/docs/extract` and `/docs/screenshot` were 404s behind what had just become those products' *primary* CTA, because `ENDPOINT_DOCS` is a `Partial<Record<…>>` and a missing key compiles silently.

> **1.12.0** (2026-09-05): **the Converter stops trusting a server, and Helix gets a document-conversion tool that isn't the same thing.** Two conversion surfaces exist now, deliberately unrelated: one runs entirely in a visited tab and touches no server ever, the other is a narrow agent-facing API endpoint that never runs on a client. Building them as one feature under one name was the mistake being corrected here — `apps/converter-api` (Fastify, ffmpeg/sharp, account-gated, 5GB server uploads) is deleted outright, not deprecated.

**The consumer converter is local now, for real.** `apps/converter` keeps its Next frontend, its port, and every UX decision `CONVERTER-CONTRACT.md` already specified — the dropzone states, the format picker, compression presets, queue rows, notifications, Web Audio chimes — because those were UI decisions independent of where the bytes went. What changed is where the bytes go: nowhere. Video/audio/GIF runs through `@ffmpeg/ffmpeg` in a Web Worker; **the multithreaded core was tried first and deadlocked mid-encode on every input tested** — a known pthread/Atomics failure class under sandboxed browser environments — so it ships single-threaded, which encoded a 2s clip in under 4s and never hung. Images go through `@jsquash`'s WASM codecs plus `utif2` (TIFF) and `libheif-js` (HEIC/HEIF, decode-only). Two format-coverage gaps were found and are declared rather than silently dropped: **no wasm build can encode real HEIC** (HEVC is patent-encumbered and absent from every open codec set — the old server-side sharp path was quietly writing AVIF-in-HEIF, not real HEIC either, so this is arguably a correction, not a regression), and **`libvpx-vp9` hangs indefinitely after the first frame** in `@ffmpeg/core`, so WebM/VP9 output is off the table and the default-target suggestion now proposes `mov` instead.

**The interesting engineering problem was Next's own bundler.** Webpack 5's native worker splitting and `worker-loader` both break Next's RSC client-reference-manifest plugin the moment the worker's import graph reaches `libheif-js` or jsquash's lazy WASM loaders. The fix sits entirely outside Next's compiler: `scripts/build-workers.mjs` runs a standalone esbuild pass before `dev`/`build`, bundles the two workers, and copies their `.wasm` binaries into `public/workers/`, loaded at runtime by plain string path. `ConverterPanel` is `next/dynamic(..., { ssr: false })` so the server-rendered half of the app never imports that graph at all.

**A second, unrelated capability**: `POST /v1/convert` on `apps/api`, for an agent mid-crawl that needs a fetched file in a different format — a crawled PDF page rasterized to PNG/JPEG for a vision call, or PNG↔JPEG normalizing. This does not touch ffmpeg, WASM, or the browser at all; it's `apps/extract`'s existing PDF/image pipeline plus one new, narrowly-scoped dependency. **`helix_extract` had no encoder for anything** before this — `pypdfium2` only reads and re-serializes existing PDF structure, `metadata.py` reads PNG/JPEG bytes structurally for EXIF without ever decoding pixels, and its own docstring already states why Pillow was kept out ("would pull an imaging stack for tag names this module has to enumerate anyway"). Rather than silently pulling in Pillow or silently shrinking the task to something dependency-free (a BMP-only output, technically zero-dependency but practically useless — almost nothing downstream wants BMP), the gap was surfaced as a real decision. Pillow was approved, scoped exactly to PDF→PNG/JPEG page rasterization and PNG↔JPEG — nothing authors a *new* PDF, DOCX, PPTX or XLSX, because that direction has no honest path without a much heavier dependency (`reportlab`/`weasyprint`-class) and is a separate decision for whenever it's actually needed. Synchronous, matching `/parse`'s pattern — single-page/single-image work has no business in the job queue. It appears as an MCP tool automatically, generated from the OpenAPI entry the same way every other endpoint is, with zero hand-written MCP code.

**A third piece closes the loop between the two**: an "Ask AI" affordance inside the local converter, modeled conceptually (not literally — the codebases don't share code) on how Cortex's own file-utilities feature lets an agent drive a conversion — a closed verb/schema table the model selects into, never a command it authors, always reviewable before it runs. Typed intent ("make this a small GIF for Discord") resolves through the operator's own BYOK provider key — direct browser-to-provider, no server in between, because inventing one to hold a shared credential would have reintroduced the exact central trust point the local rearchitecture removed. The security tradeoff of a provider key sitting in `localStorage` (XSS-readable) is stated in the Settings UI copy, not silently accepted. **The correctness guarantee is structural, not a claim**: `lib/ai/resolve.ts` calls the identical `validateConvertOptions`/`validateCompressOptions`/`validateGifOptions`/`validateImageOptions` functions the manual picker path calls, imported directly rather than re-implemented — so the AI path and the manual path cannot drift apart, by construction. Two real bugs surfaced by this discipline during testing, before shipping: `fps`/`width` and image `quality` weren't reaching the object actually passed to their validators, which would have let out-of-range values through unvalidated. A failed or absent AI call — no key configured, network failure, a model returning something outside the schema — always falls back to a fully interactive manual picker; the AI layer is additive by construction, never a dependency of the working path.

**Also**: a dashboard playground "Convert" tab exercises the real `/v1/convert` server endpoint (not a WASM engine embedded a second time in a different app) — thin UI over a real API, the same as every other playground tab, with a "need full media conversion?" link out to the standalone converter when `NEXT_PUBLIC_CONVERTER_URL` is set. The dropzone drag-and-drop logic that `metadata-form.tsx` had inline (a dragDepth counter, never extracted) is now `components/playground/file-dropzone.tsx`, shared by both forms rather than duplicated a third time. Separately, `/screenshot` (added in the previous release as route-only packaging around `/scrape`) now genuinely skips markdown extraction instead of just narrowing the response envelope — gated behind a new `skipExtraction` flag on `runPipeline`, exercised only when a request's formats are exactly `['screenshot']`. This mattered because extraction output feeds both `detectBlock` and the success-path escalation check, so the branch conditions needed real fixing, not just a bypassed function call; the fix was mutation-tested by reverting each guard individually and confirming the right tests failed both times (3 for the extraction-call guard, 8 — including pre-existing tests — for the branch-condition fix) before restoring it. A real gap surfaced honestly rather than glossed over: **there is no fixture corpus of real-world block/challenge pages anywhere in this repo**, only small synthetic HTML strings, so block-detection accuracy under `skipExtraction` is verified against those synthetic cases and not against a real Cloudflare/DataDome/PerimeterX/Akamai capture.

Verified: **apps/api** 82 files / 1219 tests passing, `tsc` clean; **apps/converter** typecheck clean, 56/56 unit tests, 9/9 Playwright e2e passing against a real running instance including a genuine (non-mocked) ffmpeg.wasm video conversion and jsquash image conversion; **apps/extract** 249/250 (the one failure is a pre-existing, unrelated missing local package). **Not verified**: `next build` for `apps/converter` fails with an EISDIR error on this Windows/exFAT checkout — the same class of pre-existing filesystem quirk `apps/dashboard`'s build has hit repeatedly in earlier releases, confirmed here against a clean, committed, untouched file, not a regression from this work; `next dev` (what the e2e suite actually exercises) is unaffected.

> **1.11.3** (2026-09-04): **the container only ever had Chromium.** 1.7.0 made Firefox and WebKit selectable per request, but `apps/api/Dockerfile` has installed `chromium` alone since before that — so any deployment that honoured `engine: 'firefox'` failed at launch with Playwright's own message, which names a cache path and says nothing about how to fix it. The install line now takes a `HELIX_BROWSER_ENGINES` build arg defaulting to `chromium`: the extra engines are opt-in rather than doubling every image for something most instances never ask for, and `--build-arg HELIX_BROWSER_ENGINES="chromium firefox"` is the whole fix. `BrowserPool` maps the executable-not-found failure onto that arg, so the error names the remedy instead of a path inside the image. This was the last unaddressed item from 1.7.0's own "not verified" list.

> **1.11.2** (2026-09-04): **one schema file you can actually run twice.** `supabase/schema.sql` was already the whole database in one file — 11 API plus 8 hosted migrations with the `schema_migrations` rows seeded so the API finds nothing to do at boot — but it is the *fresh-project* bootstrap and says so, using bare `CREATE TABLE`. Against a project that already has the schema it fails on the first statement, which makes it useless for the thing an operator most often wants: confirming a live database matches the migrations, or topping up one that is partly applied. `schema-idempotent.sql` is generated from it and is safe to re-run — guarded creates, policies and triggers dropped first, `CREATE TYPE` wrapped against `duplicate_object`. Verified by running it against the live project twice: clean both times, and the 1.11.1 browser hardening still holds afterwards. Two bugs surfaced only because it was actually run rather than reasoned about — `CREATE TYPE job_type   AS ENUM` has repeated spaces that a single-space pattern missed, and the `chunks` table is created inside an `EXECUTE $sql$` block where a line-anchored pattern cannot reach it. `check-schema.mjs` now guards both files, so `pnpm test` fails if either drifts from the migration directories. `HANDOFF.md` and `TODO.md` were two days stale at 1.2.0 — 35 commits behind — and `TODO.md` was in fact an editor-extension scratch file; both now describe the real state.

> **1.11.1** (2026-09-04): **two tables were readable and writable by anyone holding the publishable key.** Supabase grants `anon` and `authenticated` full DML on every table in `public` by default, and PostgREST serves them at `/rest/v1` to whoever holds the browser key — which ships in the bundle and is not a secret. RLS is what makes that grant inert, since a table with RLS on and no policy denies everything, and that is why most of the schema was already safe. But `request_usage` (011) and `uptime_samples` (009) are created by the **API's own migration runner**, which has no reason to know Supabase's roles exist, so they were created with RLS off. Confirmed against the live project rather than inferred: both returned rows to the publishable key, and an anonymous `INSERT` into `uptime_samples` was refused only by a not-null constraint — `23502`, a data error, not a permission one. That is an authorized write, and `uptime_samples` is what the public status page reports from. `0008_browser_role_hardening.sql` enables and forces RLS on both and revokes the browser grants outright, belt and braces, so a policy added later for an unrelated reason cannot silently re-open write access. Verified after applying: anonymous reads and writes now return `401`/`42501`, the dashboard's usage panel still reads fine because it goes through `service_role`, and the API is untouched at 39ms.

**This does not make RLS protect `/v1/*`, and the attempt to do so was abandoned deliberately.** The design would have keyed policies on a per-request `helix.api_key_id` set from `request.apiKey.id` — the *same variable* the application-layer filter already reads, from the same request. That is the first line of defence restated in SQL, not a second one: it catches a route that forgets to scope, and nothing else. Three further findings settled it. `crawl_state` has no tenant column at all and is globally unique on `url` by design — it is a shared cache of content hashes and ETags, so policying it either breaks incremental crawl or needs a schema change that multiplies the cache per tenant. The fire-and-forget `last_used_at` stamp and the usage flush both swallow their errors on purpose, so under RLS they would fail **silently** and usage would simply stop recording. And the pooled-connection hazard is real: 53 call sites use `pool.query()` against a 20-connection pool, so any non-transaction-local setting leaks the previous tenant's identity to the next request. The honest version of that work keys on `profile_id` from the Clerk claim rather than the API key, and it is a separate project.

> **1.11.0** (2026-09-04): **three cross-tenant holes closed, five untested routes covered, and the SDK finally reaches every endpoint.** A polish pass turned into a security pass, because the first thing it found was that nothing was enforcing the hosted trust boundary at all.

**The root cause, which explains all three holes at once.** `0001_hosted_identity.sql` adds `api_keys.profile_id` and RLS policies — `jobs_select_own`, `monitors_select_own` — and grants every one of them `to authenticated`, the PostgREST role a browser uses. **The API connects as `postgres`, the table owner, which bypasses RLS entirely.** So the hosted deployment had an ownership model for direct browser reads and no authorization whatsoever on any `/v1/*` request. One codebase serves two trust models and there was no gate between them; the flat model is correct in self-host and a vulnerability the moment several people share an instance.

**What that left open.** `GET /v1/keys` enumerated every key on the instance — ids, names, last-used times, effectively a tenant census — and `DELETE /v1/keys/:id` was `WHERE id = $1`, so **any hosted tenant could revoke every other tenant's credentials**, which also orphans their BYOK config since `provider_keys` is keyed on `api_key_id`. `/v1/jobs/*` queried `WHERE id = $1` with no key predicate, and `fetchJobView` spreads `...doc.content` into `data[]` — so that is not a status leak but **the full scraped corpus**, with `/jobs/:id/errors` additionally exposing crawled URLs and the victim's tier and profile escalation posture. A job id is not a capability token: it appears in the 202 body, in webhooks, in `localStorage`, in support tickets. `GET /v1/usage/all` returned per-key traffic across the instance; its own comment said hosted must never call it, which is documentation rather than a control, and combined with the key names from `/v1/keys` it becomes a named competitive-intelligence feed.

**The fix is a trust-model gate, not a permission check.** `HELIX_MULTI_TENANT`, default off so upgrading a self-host instance changes nothing. Set, it withholds `GET /v1/keys`, `DELETE /v1/keys/:id` and `/v1/usage/all` from registration entirely — additive, because nothing calls them there: the dashboard mints keys by direct Supabase insert. And it scopes jobs with `AND (api_key_id = $N::uuid OR api_key_id IS NULL)`, the disjunct keeping pre-existing and unattributed rows readable rather than orphaning them on upgrade. The scoping had to reach `/crawl/{id}` and `/batch/scrape/{id}` too, which serve the same rows through the same helpers — closing `/jobs/{id}` alone would have moved the hole rather than shut it. `monitor.ts` needed nothing: its `load()` helper already checks ownership across all seven sub-routes, and it is the pattern the rest now copies. **`DEPLOY.md` carries the flag as required for hosted**, because a security fix that needs an unwritten operator action is not a fix — and its verification step, which previously told operators to `curl /v1/keys` and treat a 200 as success, now expects a 404 there.

**Five routes had no tests at all** — `keys`, `internal`, `jobs`, `health`, `usage`, two of them auth boundaries. All 17 controls were mutation-tested: deleted, the suite re-run, restored. Three survived at first, and the cause is worth recording — the test doubles were re-implementing the `WHERE` clauses they were meant to be checking, so deleting the real predicate changed nothing. The fakes now parse the predicate out of the statement text. The same trap appeared once more in the authorization work, where an `OR true` widening survived for the same reason. **A fake that restates a clause silently absorbs that clause's deletion**, and a mutation run that cannot fail is the same failure as a test that cannot fail.

**The crawler was losing pages and calling it success.** `job_tasks.claimed_at` was written on claim and nulled on release and **never read in a WHERE clause** — nothing reclaimed it. > **1.4.0** (2026-09-03): **the Metadata API** — Helix's sixth product endpoint, and the first that answers what a file *reveals* rather than what it says. `POST /v1/metadata` scans a PDF, DOCX, PPTX, XLSX, PNG or JPEG for EXIF, GPS, XMP, PDF DocInfo and Office docProps (core/app/custom); `POST /v1/metadata/scrub` returns the cleaned file **as the response body** with the report in `X-Helix-Metadata-Report`, so a caller streams it straight to disk instead of unwrapping base64. Same intake as `/parse` — multipart `file` or a `url` fetched through the same SSRF check on every redirect, the same upload ceiling and in-flight cap — because duplicating that policy is how the second endpoint gets it wrong.

The engine (`apps/extract/helix_extract/metadata.py`, no third-party metadata library) rests on three decisions. **Findings are ranked, not listed**: each carries a `risk` band and a `category` set from the key it was read from, then raised — never lowered — when the value itself looks like an email address or a home-directory path. That value-shape rule is what catches a `Template` pointing at `C:\Users\jroe\...` and a partner's email in a custom docProp, neither of which any key vocabulary would have flagged. GPS is additionally resolved to a decimal `Coordinates` pair, since a raw DMS triple is the least readable form of the most consequential finding in a consumer photo. **Removal is structural, not cosmetic**: a metadata segment is dropped whole rather than emptied, because a zero-length APP1 still tells a reader the file once carried EXIF; OOXML containers are rebuilt with flattened entry timestamps, since a zip entry's own mtime leaks what the scrub just removed; image data and rendering chunks (gAMA, ICC) are never touched. **What a scrub achieved is measured, not assumed**: the PDF path re-scans its own output and reports whatever survived under `retained` with `removable: false` (pypdfium2 cannot write DocInfo), and a Word `comments.xml` is kept deliberately with a warning, because dropping a part a relationship still points at corrupts the document. A caller acting on "clean" while something remains is the one failure this endpoint exists to prevent, so `retained` renders first and louder than `removed`.

## What this is

Self-hostable, BYOK web-data API (scrape · parse · search · crawl · interact · monitor) with a hosted app at helix.dev. Three runtimes behind one HTTP surface: `apps/api` (TypeScript, Fastify, Playwright pool, jobs), `apps/fetch` (Rust, TLS identity), `apps/extract` (Python, parsing/LLM/embeddings), Postgres + pgvector.

Interact (`apps/api/src/routes/interact.ts`, `browser/sessions.ts`, `browser/interact-actions.ts`, `browser/screencast.ts`): sessions lease a page from the Playwright pool (`BrowserPool.lease`), bounded by `HELIX_INTERACT_MAX_SESSIONS` / `_IDLE_TIMEOUT_SECONDS` / `_HARD_TIMEOUT_SECONDS`; the live view at `/v1/interact/live/{id}?token=` is token-authenticated (the auth hook skips that prefix) and streams CDP screencast frames over SSE. `HELIX_PUBLIC_URL` builds the live-view link.

## v1.0.0 — the last gaps closed (2026-08-29)

**Vector destinations are live.** `POST /v1/crawl` takes `destination` ({type: qdrant|pgvector, collection, namespace, upsertMode}) the way openapi.yaml already claimed. Each stored page is chunked and embedded through helix-extract `POST /chunk` (embed:true) and upserted; `ensureCollection` fires once per job; a failure is recorded as a `vector_store` row in fetch_failures and counted in the job's `usage.vectorFailures` rather than losing the page. `upsertMode: append` mangles the anchor with a UUID so each call makes a fresh point. GOTCHA fixed in the same pass: the embed call's timeout was 30s, but the FIRST embed loads the model from disk and takes longer, so the first crawl anyone ran with a destination always timed out while every later one worked — it is 180s when embedding, 30s otherwise.

**M8 Enrich** (`apps/api/src/enrich/`, `routes/enrich.ts`, `apps/extract/helix_extract/enrich.py`). `POST /v1/enrich` takes a subject plus a field list and answers only from pages it read. Phased: metadata/JSON-LD first, model last. Every model-proposed value is checked against fetched content — citation must be a real passage in a page actually read, and the value must appear inside it — and anything failing becomes `null` with a reason. Confidence is an ordinal band (`high` = read out of markup by this code; `medium` = model-proposed and verified; `low` = booleans), explicitly not a probability and not calibrated. Untrusted page text is fenced with an ASCII marker whose terminator is stripped from the payload, and the wrapped type is branded so slicing it will not compile; a clipped payload tells the model how much was cut. 11 of 12 controls fail a test when deleted; the twelfth was deleted for surviving.

**Enrich yield depends on the model, and it fails closed.** Three identical runs against `gemma4:latest` returned one grounded answer and two `value_not_in_citation` refusals. That is the control working, not a bug: a small local model paraphrases rather than quoting, and a citation it cannot reproduce verbatim is discarded rather than trusted. The consequence is a real yield cost on weak models — expect nulls where a frontier model would ground — and the tradeoff is deliberate, since the alternative is confident invention. Any change here must not soften the check to raise yield.

**WebSocket live view** (2026-08-29, the one item 1.0.0 shipped without): `/v1/interact/live/{id}/ws` beside the SSE stream, not replacing it. Costs one dependency, `@fastify/websocket` (Fastify 5). Same view-token auth, same 4-viewer cap, same drop-oldest backpressure — a socket has no `write()` return value, so queue depth (`bufferedAmount` over 256KB) stands in. Messages are JSON `{type: session|frame|ping|closed, data}`; a rejected token closes 4401, a full session 4429. Inbound messages are ignored: the link carries no authority to act. Verified live — a real session streamed 17KB JPEG frames over the socket, and SSE was re-checked in the same run to confirm it still works.

**Monitors**: business-hours windows (`schedule.window`), which RESTRICT the cron and never widen it — a combination that can never fire is rejected at write time — and field-level JSON diffs (`jsonOptions`, migration 008) that run only once a change is already firing, so a quiet check pays for no model call.

**`@helix/sdk`** (packages/sdk-ts, was an empty directory): typed client over every path in openapi.yaml, no runtime dependencies. Where the spec and the dashboard's hand-written client disagreed the spec won — scrape actions and interact actions are separate unions, stored providers (4 cloud) are separate from the 7-value per-request extract override.

**Local models are browsable**: `GET /v1/providers/{provider}/models` reads Ollama's native `/api/tags` (deriving the native root from the stored `/v1` base URL) or an OpenAI-style `/v1/models`, and Settings → Model providers offers them beside the free-text field.

Two bugs that would have shipped, both found only by running against a real model rather than a mock. `/v1/agent/schema` accepted no `provider`, and helix-extract's auto-pick walks cloud vendors only by design, so an instance whose sole provider was a local runtime could not use it at all. With that fixed it answered, and always returned `properties: {}` — `_strictify` in `schema_compiler.py` stamped `additionalProperties: false` onto objects declaring no properties, which forbids every key, so the meta-schema's own `properties` field was structurally unfillable and schema design could never emit a field.

Stored overrides merge into `config` immediately after the pool is created and before any consumer is constructed, so "restart required" is truthful — verified live: an override of `crawlMaxDepth: 7` survived a restart and made the API reject `maxDepth: 20`, which the env default of 50 allows.

Rotating the encryption key used to orphan every stored provider key (`decryptSecret` takes one key; rows carried no version). `provider_keys.key_version` plus `rotate.ts` now re-encrypt inside one transaction, decrypting everything before writing anything, so a wrong key aborts with nothing changed. ## Batch scrape and the stealth chain (2026-08-26)

`POST /v1/batch/scrape` takes a list of URLs and returns one job. It runs on the crawl worker rather than beside it, and batch semantics come from options the frontier already understood: `maxDepth: 0` rejects every discovered link as too deep, `sitemap: 'skip'` removes the other source of unasked-for URLs, and `allowExternal` lets the list span hosts. The `jobs` enum already carried `batch_scrape`, so no migration. Async only. Verified live across two hosts - `example.com` links to `iana.org`, and the job finished with exactly the two supplied tasks.

**The stealth chain was not what the docs said.** Three links, and only one was real:

- **Transport - real.** `apps/fetch`'s `resolve()` maps a profile name onto a `wreq-util` `Emulation` preset (13 identities), maintained upstream against actual browser captures. The JSON definitions do not drive this; `load_all()` in `profile.rs` is a stub with a TODO and never reads them.
- **JS layer - was dead, now applied.** The definitions carried WebGL strings, core count, memory, timezone and screen that *nothing read*. A scrape naming a profile got the right transport identity and the host machine's real fingerprint - the exact contradiction profiles exist to prevent. `apps/api/src/browser/profiles.ts` now injects it via `addInitScript`, and `profileUsed` is reported the way the fetch tiers already did. Canvas is perturbed deterministically from the profile id, because a value that varies between two reads is itself the tell.
- **Capture - built, and the chain now closes.** `tools/capture` records a real browser's JS surface (`@helix/capture`). It refuses a `HeadlessChrome` user-agent, a SwiftShader renderer and an unstable canvas, because a bad recording marked `verified: true` is worse than none.

**The version ceiling is gone (2026-08-26).** `wreq-util 0.1` stopped at Chrome 137 while browsers run 148+, so every capture paired a user-agent the transport layer could not present. The pin comment named the cause: `wreq 0.16` needs rustc 1.98, and the toolchain was 1.95. After `rustup update`, apps/fetch moved to `wreq 0.16` + `wreq-util 0.2` and `available()`/`resolve()` grew from 13 identities to **44** (Chrome 131-149, Edge 127-148, Safari 17.5-26.4 including iOS); the default is now `chrome-149`. The release binary reports `profiles_loaded: 44`, and a live fetch returns `profile_used: chrome-148`.

`chrome-148-windows.json` is the first `verified: true` definition — recorded with `--executable` against Playwright's chromium-1223 build, which is Chrome 148. Playwright keeps more than one Chromium, and the older one is often the version `wreq-util` carries.

The 0.16 API changes were mechanical but worth knowing: `Emulation` became `Profile` (aliased as `Identity`, since profile.rs has its own `Profile`), `wreq::Url` gave way to `http::Uri`, and `Attempt::url()`/`previous()` are now public fields.

`load_all()` in apps/fetch was a stub that never opened the JSON, which is why `ProfileError` and `validate()` were dead code. It now reads `packages/profiles/definitions`, refuses to boot on an incoherent profile, and warns per definition that was never captured or that names an identity the transport layer falls back from. `health()` separates the two counts it used to conflate: `profiles_loaded` is the identities this build presents (44), `definitions_loaded` is the JSON actually read (2).

`chrome-149-macos` is gone — a fabricated sample whose id `resolve()` fell back from. `chrome-137-macos` stays because `chrome-137` resolves and has no other definition, but it is `verified: false`, describes a macOS machine that cannot be captured from this Windows box, and both tiers log a warning on every use.

A naming trap worth keeping in mind: `resolve()` echoes back whatever name it is given, so comparing its returned id to a definition's proves nothing — check membership in `available()`. A test of mine passed while broken for exactly that reason.

## Sign-in fix, the auth surface, and the /app backdrop grid (2026-08-27)

**Signed-out `/app` went to Clerk's hosted portal** (`fluent-eft-4786.accounts.dev`) instead of `/sign-in`. `auth.protect()` runs in middleware and reads its sign-in path from the `clerkMiddleware` options or `NEXT_PUBLIC_CLERK_SIGN_IN_URL`; the `signInUrl` prop on `ClerkProvider` only covers client components. Both paths are now passed in code, plus `signInFallbackRedirectUrl="/app"` / `signUpFallbackRedirectUrl="/onboarding"`, so env is no longer load-bearing. Diagnose Clerk in a browser (`research/firecrawl-capture/probe-clerk-signin.mjs`) — `curl` without `Accept: text/html` gets Clerk's non-page 404 rewrite, which is not what a person sees.

**Auth surface.** `AuthFrame` now carries the hero's `GridCells` (crosshairs, markers, ✦ nodes, clusters), masked clear behind the Clerk card, plus two new ambient pieces in `components/marketing/ocean.tsx`: `AsciiOcean` (a three-sine height field rendered as glyphs, violet crests on an ink swell, along the bottom) and `AsciiWave` (one travelling sine beside the title). Same contract as `AsciiHelix` — one 12fps ticker, paused off-screen, settled frame under reduced motion, hidden below `lg`. `useInView` is exported from `ambient.tsx` for them.

**/app grid is one shell-level backdrop**, not per page. `app-shell.tsx` mounts `AppGrid` (now with `sparkles`, pinned ✦ nodes from row 3 down) as `sticky top-0 z-[-1] h-0` inside `main.isolate.[container-type:size]`, sized `h-[100cqh]`. Three details are load-bearing: sticky with zero height takes no space; `cqh` sizes it to the scroll area rather than the viewport; `z-[-1]` inside `isolate` paints it below in-flow content. The first attempt — a `min-h-full` wrapper around children — put the absolutely positioned grid *above* any page whose root was not positioned (absolute siblings paint over in-flow blocks regardless of DOM order) and broke `PageFrame`'s own `min-h-full`, so the overview's column borders stopped at content bottom. `PageFrame` and the agent page no longer mount their own grid; pages that bypass `PageFrame` paint `bg-background` on their content panel, the contract `FrameRow` already follows.
