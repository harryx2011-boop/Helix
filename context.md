**Documents are a third engine, and the matrix is written out rather than derived.** Video, audio and images all meet in the middle as frames or samples, so any decodable input reaches any encodable output; documents have no universal intermediate — a spreadsheet is rows, Markdown is a tree, a PDF is a page description. `DOC_TARGETS` therefore lists the real pairs per source, and both the format picker and the 43 generated `/convert/[pair]` routes read from it, so a pair the worker would refuse can never be offered. Two edges are deliberately one-way: **`xls` is input-only** (ExcelJS has no BIFF8 writer, and a second spreadsheet dependency to emit a 1997 binary format is not worth it), and **a PDF never becomes a spreadsheet** — a PDF table is a visual arrangement of glyphs, and reconstructing cells from it is a heuristic that produces confidently wrong numbers, so PDF in gives text/Markdown/HTML only and a scan says it needs OCR rather than returning an empty file. A test asserts that edge stays absent.

**The kind tabs came from reference images, with one deliberate departure.** Video / Audio / Image / Document sit above the dropzone and swap the accepted-format line beneath it; GIF is not a fifth tab despite being its own `FileKind` in the engine, because to anyone picking a file it is an image format. The refs also read "No file size limits", which is not true here — there is a real 2 GB per-file ceiling bounded by what a tab can hold in memory — so the copy says that instead.

**Three real bugs surfaced only by driving a browser, none by the compiler.** ExcelJS resolves its own Buffer-alike rather than a plain `ArrayBuffer`, which is not transferable: every `csv → xlsx` failed at `postMessage` with *"Value at index 0 does not have a transferable type"*, now caught by a `normalize()` gate every payload passes. The Quality slider rendered for documents, which have no quality dial. And a **pre-existing** interaction bug the document work happened to expose: a collapsed file row is a `grid-rows-[0fr]` + `overflow-hidden` accordion, which clips its contents visually but leaves them in the tab order and hit-testing — a collapsed row's own heading was painting over the Format buttons above it, making them unclickable. > **1.16.1** (2026-09-05): **cancelling a crawl now stops the work it was paying for.** `DELETE /v1/crawl/{id}` marked the job cancelled and the frontier stopped handing out pages, but anything already in flight ran to completion — including the per-page `extractClient.structured()` call added in 1.14.0, which bills the caller's own provider. A job-scoped `AbortController` is aborted when the cancellation poll sees the flip (and on worker shutdown), and its signal now reaches both the pipeline fetch and the structured call.

**Three things had to be true for that signal to be worth having, and only the first was obvious.** An abort must not be *counted* as a failure: the catch around structured extraction incremented `jsonFailed` and logged a warning, so a cancelled crawl would have reported dozens of pages the extractor "tried and lost", and any retry layer reading that count would re-fire the call the cancellation had just killed. A page the pipeline reports as `aborted` must not be written to `fetch_failures` either — but only when the job itself caused it, because an `aborted` from anywhere else still has to reach the frontier or the row stays leased and `pending` never drains, which is a spin until the lease expires. The cancelled case is deliberately left leased: `frontier.release()` runs immediately afterwards and returns it to `queued`, so a resumed job retries the page rather than skipping it as done or spending an attempt on it.

**The bug underneath was that the poll could not fire at all.** With one slow page outstanding and nothing queued, the loop blocked on `await Promise.race(inFlight)`, which resolves only when that page finishes — so a crawl whose last page took two minutes could not notice it had been cancelled for two minutes. The signal existed and nothing reached the check that fires it. `raceInFlight()` now races the in-flight set against a timer bounded by the poll interval, so the check is never more than `CANCEL_POLL_MS` away. Found by a test that kept a page outstanding for 2.5 seconds; it passed at 60ms for the wrong reason before that.

> **1.15.0** (2026-09-05): **the Converter records your screen, and two options that were declared but ignored now do something.** `apps/converter/app/record` captures a window, a tab or the whole screen for up to 30 minutes, with an optional microphone track mixed in through Web Audio, then hands the result to the ffmpeg worker the rest of the app already uses — so a WebM capture becomes an MP4 or a GIF without a second encoder. Everything stays in the tab: the capture, the encoding, the storage, and the only byte that leaves is a file the user saves to their own disk.

**Recordings live in IndexedDB, not localStorage, and that is not a style choice.** localStorage holds strings in roughly 5 MB per origin; a 30-minute capture is 300 MB to 2 GB of binary, so a recording written there throws `QuotaExceededError` within seconds. IndexedDB stores Blobs natively, is bounded by disk rather than a fixed cap, and — unlike the blob URLs the converter uses elsewhere — survives a reload, which matters for something a person spent half an hour making. Chunks are written **as they arrive**, one per second, rather than accumulated in an array and saved at the end: a crash at minute 29 costs one second, not 29 minutes. A row left mid-write by a closed tab is pruned before the list renders, because presenting a partial capture as a finished one is worse than not offering it — the user cannot tell which minutes are missing. VP9 is used here despite 1.12.0 taking WebM off the table for conversion: that hang was `libvpx-vp9` inside `@ffmpeg/core`, and this is the browser's own `MediaRecorder`, a different encoder entirely.

**Two bugs that only a real browser could find.** The trim handles could be pushed until they *met* — `end - 0.1` rounds back to `end` at a tenth-second step, giving ffmpeg a zero-length range it accepts and answers with an empty file; the clamp now rounds to the step and the export refuses a selection below it. And the export's blob URL was revoked the instant it was created: the cleanup effect had `result` in its dependency array, so setting the result re-ran the effect and the *previous* cleanup released the URL the Save link had just been given. The URL is held in a ref and released on unmount only. Both were found by driving the page with a real Chromium and reading the exported bytes — the MP4 begins `ftypisom` and the GIF `GIF89a`, which is the check that distinguishes a working export from a plausible-looking failure.

**`ImageOptions.fit` was declared, validated, and then ignored.** The image worker hardcoded jSquash's `fitMethod: 'stretch'`, so `cover`, `contain`, `inside` and `outside` all produced the same stretched output. jSquash offers only `stretch` and `contain`, so the other three are computed before the resize now, with `cover` doing a real centre crop rather than letterboxing. A new `thumbs` op joins the engine union: a poster frame at a timestamp, a contact-sheet sprite whose frames are spaced across the whole clip, or an animated WebP preview. A sprite wider than 16,384px is rejected at the validator rather than failing late in wasm.

> **1.11.0** (2026-09-04): **three cross-tenant holes closed, five untested routes covered, and the SDK finally reaches every endpoint.** A polish pass turned into a security pass, because the first thing it found was that nothing was enforcing the hosted trust boundary at all.

**The root cause, which explains all three holes at once.** `0001_hosted_identity.sql` adds `api_keys.profile_id` and RLS policies — `jobs_select_own`, `monitors_select_own` — and grants every one of them `to authenticated`, the PostgREST role a browser uses. **The API connects as `postgres`, the table owner, which bypasses RLS entirely.** So the hosted deployment had an ownership model for direct browser reads and no authorization whatsoever on any `/v1/*` request. One codebase serves two trust models and there was no gate between them; the flat model is correct in self-host and a vulnerability the moment several people share an instance.

**What that left open.** `GET /v1/keys` enumerated every key on the instance — ids, names, last-used times, effectively a tenant census — and `DELETE /v1/keys/:id` was `WHERE id = $1`, so **any hosted tenant could revoke every other tenant's credentials**, which also orphans their BYOK config since `provider_keys` is keyed on `api_key_id`. `/v1/jobs/*` queried `WHERE id = $1` with no key predicate, and `fetchJobView` spreads `...doc.content` into `data[]` — so that is not a status leak but **the full scraped corpus**, with `/jobs/:id/errors` additionally exposing crawled URLs and the victim's tier and profile escalation posture. A job id is not a capability token: it appears in the 202 body, in webhooks, in `localStorage`, in support tickets. `GET /v1/usage/all` returned per-key traffic across the instance; its own comment said hosted must never call it, which is documentation rather than a control, and combined with the key names from `/v1/keys` it becomes a named competitive-intelligence feed.

**The fix is a trust-model gate, not a permission check.** `HELIX_MULTI_TENANT`, default off so upgrading a self-host instance changes nothing. Set, it withholds `GET /v1/keys`, `DELETE /v1/keys/:id` and `/v1/usage/all` from registration entirely — additive, because nothing calls them there: the dashboard mints keys by direct Supabase insert. And it scopes jobs with `AND (api_key_id = $N::uuid OR api_key_id IS NULL)`, the disjunct keeping pre-existing and unattributed rows readable rather than orphaning them on upgrade. The scoping had to reach `/crawl/{id}` and `/batch/scrape/{id}` too, which serve the same rows through the same helpers — closing `/jobs/{id}` alone would have moved the hole rather than shut it. `monitor.ts` needed nothing: its `load()` helper already checks ownership across all seven sub-routes, and it is the pattern the rest now copies. **`DEPLOY.md` carries the flag as required for hosted**, because a security fix that needs an unwritten operator action is not a fix — and its verification step, which previously told operators to `curl /v1/keys` and treat a 200 as success, now expects a 404 there.

Each library now branches on `HOSTED`; the self-host path is byte-for-byte what it was, and since `HOSTED` is a build-time env read, the branch is dead-code-eliminated from the static export. **The key that path uses is the interesting part**: keys are stored SHA-256 hashed, so no plaintext can be read back. Each hosted profile therefore gets one dedicated `api_keys` row minted lazily (`0006_dashboard_keys.sql`), AES-256-GCM encrypted with `HELIX_KEY_ENCRYPTION_KEY` and cached on `profiles`; it is decrypted only inside a route handler and never reaches a browser. `provider_keys` is keyed on `api_key_id`, so BYOK config lands on it with no schema change. The `/internal/keys` mirror was rejected: it can only import a key the caller already generated, and `0001`'s own comment says hosted deliberately avoids that sync.

**Three defects in that design, found by review and fixed before shipping.** `supabase/schema.sql` — the fresh-project bootstrap — had silently drifted across four migrations, so a new hosted project would have been created without `0006`'s column-grant revocation and a signed-in user could have read their own ciphertext and IV straight off PostgREST. Regenerated to 10 API + 6 hosted; the `Sources:` line is worth a CI check, since drift is invisible until someone provisions. The internal key was also *listed on the user's own Keys page with a Revoke button* — clicking it bricked that account's playground, agent and provider settings permanently, because the cache stayed populated so the mint branch was never reached again, and it orphaned every BYOK credential stored against the dead key id. `listApiKeys` now takes an `excludeId` (filtered on id, not name, so the name is not load-bearing), DELETE 404s on it, and `resolveDashboardApiKey` **verifies its cache instead of trusting it** — a revoked row or a failed decrypt is treated as a miss, which also makes `HELIX_KEY_ENCRYPTION_KEY` rotation survivable where it would otherwise have bricked every account. And the mint was read-then-write with no constraint, so the several calls the app fires on mount each minted a live key and only the last was retained; it is now a conditional update that revokes its own loser and reads back the winner.

**Engines are a choice, and the ladder is unchanged.** `browser/engines.ts` centralises everything that differs per engine, because Chromium's `--no-sandbox` and friends are Chromium-only switches that break a Firefox or WebKit launch outright. Pools are keyed by engine and launched **lazily** — only the configured default warms at boot, since launching all three would spend ~3s and most of a gigabyte on engines most instances never ask for. Camoufox joins `TIER_ORDER` above chromium as an optional hardened-Firefox tier, reached over `firefox.connect` rather than bundled: it ships as a per-platform binary of a few hundred MB, the same weight that disqualified `@firecrawl/pdf-inspector` in M3. A remote CDP backend lets the chromium tier connect to Browserless/Steel/a grid instead of launching locally; its endpoint is a `guarded` setting, and non-chromium plus remote is refused outright because CDP cannot drive Firefox or WebKit. **The escalation rule held**: `DEFAULT_MAX_TIER` is `chromium`, so evidence walks a request up to chromium and stops, and camoufox is reachable only by naming it — a Cloudflare challenge never produces a camoufox attempt. The private-address guard was **verified, not assumed**: a real loopback server, probed on all three engines, all three abort with zero server hits, and the `allowPrivate` case proves the guard was what blocked it. That is now a permanent test. Two findings from those tests: Firefox accepts `isMobile` and silently ignores touch, so `metadata.mobile` reports `false` rather than lying; and a Chrome-based profile on Firefox is dropped with a warning, because a Chrome UA over Gecko is a positive detection signal — strictly worse than no spoofing, the same invariant `apps/fetch/src/profile.rs` enforces one level down.

**The crawler was losing pages and calling it success.** `job_tasks.claimed_at` was written on claim and nulled on release and **never read in a WHERE clause** — nothing reclaimed it. A SIGKILLed worker left rows at `running` forever, and the crawl then completed reporting fewer pages than it queued with no failure row to explain the gap, which is the worst possible shape for this bug. `010_task_leases.sql` adds `lease_expires_at` and `max_attempts`, with expiry evaluated by Postgres `now()` and never a timestamp computed in Node, or two machines with skewed clocks reclaim each other's live work. A second live bug surfaced in the same file: `next()` spliced items out of `#claimed`, so the frontier forgot rows still `running`, and `release()` requeued only the unstarted buffer — every page mid-fetch was stranded and `pending` under-counted, so the worker loop could exit while fetches were in flight. A separate `#inFlight` map fixes both, and `release()` now matches on `claimed_by` so a shutting-down worker cannot requeue a row another worker legitimately reclaimed. Alongside: block verdicts never reached the AIMD controller, which mattered because a Cloudflare interstitial arrives as **HTTP 200** and was being scored as a healthy fetch — the controller ramped straight into the wall. `RequestOutcome` now carries `blocked`, checked before the status code and treated as worse than a 429 (collapse to floor, 30s backoff, then a 20-fetch probation that holds the ramp down, because ramping back into an anti-bot system is how a soft block becomes a hard ban). `Retry-After` was read but never supplied, since `PipelineFailure` discarded response headers; both forms are parsed now, including the HTTP-date form implementations forget. New `crawl/sessions.ts` pins one profile, one proxy exit and one cookie jar for a session's life and rotates **on failure, not on schedule** — an identity that was accepted and kept its cookies is the one most likely to be accepted again; retirement takes two blocks rather than one, since a single block is often the page and not the identity, and a replacement starts with an empty jar because carrying cookies across is the most direct way to link two identities.

> **1.4.0** (2026-09-03): **the Metadata API** — Helix's sixth product endpoint, and the first that answers what a file *reveals* rather than what it says. `POST /v1/metadata` scans a PDF, DOCX, PPTX, XLSX, PNG or JPEG for EXIF, GPS, XMP, PDF DocInfo and Office docProps (core/app/custom); `POST /v1/metadata/scrub` returns the cleaned file **as the response body** with the report in `X-Helix-Metadata-Report`, so a caller streams it straight to disk instead of unwrapping base64. Same intake as `/parse` — multipart `file` or a `url` fetched through the same SSRF check on every redirect, the same upload ceiling and in-flight cap — because duplicating that policy is how the second endpoint gets it wrong.

The engine (`apps/extract/helix_extract/metadata.py`, no third-party metadata library) rests on three decisions. **Findings are ranked, not listed**: each carries a `risk` band and a `category` set from the key it was read from, then raised — never lowered — when the value itself looks like an email address or a home-directory path. That value-shape rule is what catches a `Template` pointing at `C:\Users\jroe\...` and a partner's email in a custom docProp, neither of which any key vocabulary would have flagged. GPS is additionally resolved to a decimal `Coordinates` pair, since a raw DMS triple is the least readable form of the most consequential finding in a consumer photo. **Removal is structural, not cosmetic**: a metadata segment is dropped whole rather than emptied, because a zero-length APP1 still tells a reader the file once carried EXIF; OOXML containers are rebuilt with flattened entry timestamps, since a zip entry's own mtime leaks what the scrub just removed; image data and rendering chunks (gAMA, ICC) are never touched. **What a scrub achieved is measured, not assumed**: the PDF path re-scans its own output and reports whatever survived under `retained` with `removable: false` (pypdfium2 cannot write DocInfo), and a Word `comments.xml` is kept deliberately with a warning, because dropping a part a relationship still points at corrupts the document. A caller acting on "clean" while something remains is the one failure this endpoint exists to prevent, so `retained` renders first and louder than `removed`.

## What this is

A frontier utility hub: self-hostable and BYOK (scrape · parse · search · crawl · interact · monitor) with a hosted app at helix.dev. Three runtimes behind one HTTP surface: `apps/api` (TypeScript, Fastify, Playwright pool, jobs), `apps/fetch` (Rust, TLS identity), `apps/extract` (Python, parsing/LLM/embeddings), Postgres + pgvector.

Interact (`apps/api/src/routes/interact.ts`, `browser/sessions.ts`, `browser/interact-actions.ts`, `browser/screencast.ts`): sessions lease a page from the Playwright pool (`BrowserPool.lease`), bounded by `HELIX_INTERACT_MAX_SESSIONS` / `_IDLE_TIMEOUT_SECONDS` / `_HARD_TIMEOUT_SECONDS`; the live view at `/v1/interact/live/{id}?token=` is token-authenticated (the auth hook skips that prefix) and streams CDP screencast frames over SSE. `HELIX_PUBLIC_URL` builds the live-view link.

## v1.0.0 — the last gaps closed (2026-08-29)

**Vector destinations are live.** `POST /v1/crawl` takes `destination` ({type: qdrant|pgvector, collection, namespace, upsertMode}) the way openapi.yaml already claimed. Each stored page is chunked and embedded through helix-extract `POST /chunk` (embed:true) and upserted; `ensureCollection` fires once per job; a failure is recorded as a `vector_store` row in fetch_failures and counted in the job's `usage.vectorFailures` rather than losing the page. `upsertMode: append` mangles the anchor with a UUID so each call makes a fresh point. GOTCHA fixed in the same pass: the embed call's timeout was 30s, but the FIRST embed loads the model from disk and takes longer, so the first crawl anyone ran with a destination always timed out while every later one worked — it is 180s when embedding, 30s otherwise.

**M8 Enrich** (`apps/api/src/enrich/`, `routes/enrich.ts`, `apps/extract/helix_extract/enrich.py`). `POST /v1/enrich` takes a subject plus a field list and answers only from pages it read. Phased: metadata/JSON-LD first, model last. Every model-proposed value is checked against fetched content — citation must be a real passage in a page actually read, and the value must appear inside it — and anything failing becomes `null` with a reason. Confidence is an ordinal band (`high` = read out of markup by this code; `medium` = model-proposed and verified; `low` = booleans), explicitly not a probability and not calibrated. Untrusted page text is fenced with an ASCII marker whose terminator is stripped from the payload, and the wrapped type is branded so slicing it will not compile; a clipped payload tells the model how much was cut. 11 of 12 controls fail a test when deleted; the twelfth was deleted for surviving.

**Enrich yield depends on the model, and it fails closed.** Three identical runs against `gemma4:latest` returned one grounded answer and two `value_not_in_citation` refusals. That is the control working, not a bug: a small local model paraphrases rather than quoting, and a citation it cannot reproduce verbatim is discarded rather than trusted. The consequence is a real yield cost on weak models — expect nulls where a frontier model would ground — and the tradeoff is deliberate, since the alternative is confident invention. Any change here must not soften the check to raise yield.

**WebSocket live view** (2026-08-29, the one item 1.0.0 shipped without): `/v1/interact/live/{id}/ws` beside the SSE stream, not replacing it. Costs one dependency, `@fastify/websocket` (Fastify 5). Same view-token auth, same 4-viewer cap, same drop-oldest backpressure — a socket has no `write()` return value, so queue depth (`bufferedAmount` over 256KB) stands in. Messages are JSON `{type: session|frame|ping|closed, data}`; a rejected token closes 4401, a full session 4429. Inbound messages are ignored: the link carries no authority to act. Verified live — a real session streamed 17KB JPEG frames over the socket, and SSE was re-checked in the same run to confirm it still works.

**Monitors**: business-hours windows (`schedule.window`), which RESTRICT the cron and never widen it — a combination that can never fire is rejected at write time — and field-level JSON diffs (`jsonOptions`, migration 008) that run only once a change is already firing, so a quiet check pays for no model call.

**`@helix/sdk`** (packages/sdk-ts, was an empty directory): typed client over every path in openapi.yaml, no runtime dependencies. Where the spec and the dashboard's hand-written client disagreed the spec won — scrape actions and interact actions are separate unions, stored providers (4 cloud) are separate from the 7-value per-request extract override.

**Local models are browsable**: `GET /v1/providers/{provider}/models` reads Ollama's native `/api/tags` (deriving the native root from the stored `/v1` base URL) or an OpenAI-style `/v1/models`, and Settings → Model providers offers them beside the free-text field.

Two bugs that would have shipped, both found only by running against a real model rather than a mock. `/v1/agent/schema` accepted no `provider`, and helix-extract's auto-pick walks cloud vendors only by design, so an instance whose sole provider was a local runtime could not use it at all. With that fixed it answered, and always returned `properties: {}` — `_strictify` in `schema_compiler.py` stamped `additionalProperties: false` onto objects declaring no properties, which forbids every key, so the meta-schema's own `properties` field was structurally unfillable and schema design could never emit a field.

## GitHub connections (2026-08-26)

Settings → Integrations connects a user's GitHub account so Helix can read what
they already have access to. Deliberately SEPARATE from the GitHub sign-in
Clerk offers: Clerk's external-account token carries the scopes sign-in asked
for, and users who signed in with Google or email have no GitHub token at all,
so a distinct OAuth App means everyone can connect and the scopes are ours.

`supabase/migrations/0002_github_connections.sql` holds one row per
(profile, github_login) — AES-256-GCM `token_ciphertext`/`token_iv` under the

LLM vendors, while a GitHub grant belongs to a person and carries expiry and
scopes.

`lib/github.ts` owns the flow and is the only module that decrypts a token —

DELETE (both scoped by `profile_id` as well as id).

an account never silently re-grants agent use the user turned off.

## Batch scrape and the stealth chain (2026-08-26)

`POST /v1/batch/scrape` takes a list of URLs and returns one job. It runs on the crawl worker rather than beside it, and batch semantics come from options the frontier already understood: `maxDepth: 0` rejects every discovered link as too deep, `sitemap: 'skip'` removes the other source of unasked-for URLs, and `allowExternal` lets the list span hosts. The `jobs` enum already carried `batch_scrape`, so no migration. Async only. Verified live across two hosts - `example.com` links to `iana.org`, and the job finished with exactly the two supplied tasks.

**The stealth chain was not what the docs said.** Three links, and only one was real:

- **Transport - real.** `apps/fetch`'s `resolve()` maps a profile name onto a `wreq-util` `Emulation` preset (13 identities), maintained upstream against actual browser captures. The JSON definitions do not drive this; `load_all()` in `profile.rs` is a stub with a TODO and never reads them.
- **JS layer - was dead, now applied.** The definitions carried WebGL strings, core count, memory, timezone and screen that *nothing read*. A scrape naming a profile got the right transport identity and the host machine's real fingerprint - the exact contradiction profiles exist to prevent. `apps/api/src/browser/profiles.ts` now injects it via `addInitScript`, and `profileUsed` is reported the way the fetch tiers already did. Canvas is perturbed deterministically from the profile id, because a value that varies between two reads is itself the tell.
- **Capture - built, and the chain now closes.** `tools/capture` records a real browser's JS surface (`@helix/capture`). It refuses a `HeadlessChrome` user-agent, a SwiftShader renderer and an unstable canvas, because a bad recording marked `verified: true` is worse than none.

**The version ceiling is gone (2026-08-26).** `wreq-util 0.1` stopped at Chrome 137 while browsers run 148+, so every capture paired a user-agent the transport layer could not present. The pin comment named the cause: `wreq 0.16` needs rustc 1.98, and the toolchain was 1.95. After `rustup update`, apps/fetch moved to `wreq 0.16` + `wreq-util 0.2` and `available()`/`resolve()` grew from 13 identities to **44** (Chrome 131-149, Edge 127-148, Safari 17.5-26.4 including iOS); the default is now `chrome-149`. The release binary reports `profiles_loaded: 44`, and a live fetch returns `profile_used: chrome-148`.

`chrome-148-windows.json` is the first `verified: true` definition — recorded with `--executable` against Playwright's chromium-1223 build, which is Chrome 148. Playwright keeps more than one Chromium, and the older one is often the version `wreq-util` carries.

The 0.16 API changes were mechanical but worth knowing: `Emulation` became `Profile` (aliased as `Identity`, since profile.rs has its own `Profile`), `wreq::Url` gave way to `http::Uri`, and `Attempt::url()`/`previous()` are now public fields.

`load_all()` in apps/fetch was a stub that never opened the JSON, which is why `ProfileError` and `validate()` were dead code. It now reads `packages/profiles/definitions`, refuses to boot on an incoherent profile, and warns per definition that was never captured or that names an identity the transport layer falls back from. `health()` separates the two counts it used to conflate: `profiles_loaded` is the identities this build presents (44), `definitions_loaded` is the JSON actually read (2).

`chrome-149-macos` is gone — a fabricated sample whose id `resolve()` fell back from. `chrome-137-macos` stays because `chrome-137` resolves and has no other definition, but it is `verified: false`, describes a macOS machine that cannot be captured from this Windows box, and both tiers log a warning on every use.

A naming trap worth keeping in mind: `resolve()` echoes back whatever name it is given, so comparing its returned id to a definition's proves nothing — check membership in `available()`. A test of mine passed while broken for exactly that reason.
