# Tilion: what it does and what Helix can take

Date: 2026-11-18. Author: Claude (research subagent). Status: research only. No code changed. Nothing was installed, no account was made, Tilion's API was never called, and its MCP server was not registered (Harry: "we take their ideas ... apply to helix and update cortex's docs and global backlog").

Legend: **[V]** read on the page named beside it. **[I]** inferred by me. **[C]** a claim by Tilion that nobody tested. Helix state comes from `context.md`, `docs/plans/2026-11-18-stealth-ladder.md` and a code check of `apps/api/src` on 2026-11-18.

## 0. Short answer

1. Tilion is hosted cloud-browser infrastructure for AI agents, backed by Y Combinator [V: https://www.ycombinator.com/companies/tilion]. It is a paid service, not self-hostable. No licence is published for the service [V: pages read]. It runs on "Fortress", which it calls its own open-source Chromium build with the fingerprint fixed in C++ [C: YC page]. I did not find or test Fortress.
2. Its home page says nothing about the product. The facts are in `docs.tilion.dev`, which is built for agents (llms.txt, every page also served as `.md`) [V: https://docs.tilion.dev/llms.txt].
3. Its core claim: sites cannot tell the agent from a scraper, and the agent reads the block page as content and fails without anyone noticing [V: YC page]. Its answer is a typed result (`content_ok`, `status`) plus automatic recovery. This is the idea most worth copying.
4. Setup is a prompt: "setup tilion.com" makes the agent read `setup.md`, then connect an MCP server by OAuth with a person signing in by emailed code [V: https://tilion.com/setup.md]. Proton's injection check scored three sections of that file 0.97 to 0.9999 on "hidden instructions". My reading is that the text is plain how-to prose, so the score is likely a false positive on long agent-addressed text. It is noted here, not acted on.
5. Speed and stealth claims ("number one on the public ComputeSDK browser benchmarks") [C: YC page]. ComputeSDK has an open benchmark repo with browser and stealth suites [V: https://github.com/computesdk/benchmarks]. Helix could run its proof runner (plan batch E) against those suites. Not run here.

## 2. Ideas to take, ranked

Order is my judgement, checked against `proton.rank` (criterion "most useful to a self-hosted scraping and agent-browser service"). The scores sit in a narrow band (0.73 to 0.80), so I treat the rank as a weak hint. I put the typed outcome above where proton put it (13th of 16) because it is Tilion's central claim.

| Rank | Idea | How it would fit Helix | Effort [I] |
|---|---|---|---|
| 1 | **Network capture report** (row 10) | A `helix_inspect` tool over the Playwright pool: load a URL, record `response` events for N seconds, return JSON endpoints, auth signals and asset counts. Scraping the JSON behind a page is often faster and steadier than the DOM | Small |
| 2 | **Save a login from the live view** (rows 14, 11) | After a person signs in through the existing live-view link, a `save-auth` call writes that host's cookies and UA into the planned `host_sessions` table. This gives it a second feeder besides `/render` | Small, after batch C |
| 3 | **Typed outcome plus caller checks** (rows 4, 5, 7) | Add `content_ok` and a `status` enum to scrape and interact results, and `expect_text`, `expect_url`, `no_results_url` inputs. Escalation then climbs when the check fails, not only on a block verdict. Add `on_deadline: continue` using existing jobs | Medium |
| 4 | **Profile versions, merge saves, login probe, identity coherence** (rows 11, 12) | Extend `host_sessions`: keep the last N versions, a `probe` (required cookie names) that refuses a bad save, and store the identity id with the cookies so replay under a different identity warns. Avoids silently clobbering a good session | Medium |
| 5 | **Session recording** (row 16) | Persist the screencast frames Helix already produces, with a manifest and a `secret: true` typing flag that pauses capture. Gives a replay of why a scrape failed | Medium |
| 6 | Human-like visit options (row 9) | `warm_entry` and `visitor` as flags on the stealth rungs. Both are robots-gated like the rest | Small |
| 7 | Own-proxy exit ladder (row 18) | Rungs: direct, then the user's own proxies, climbing only on block evidence. Fits the ladder registry (batch B10) | Medium |
| 8 | Idempotency key and a terminal record for sessions (rows 2, 3) | Small API hygiene for agents that retry | Small |
| 9 | Connect instructions on the MCP server (row 22) | One string: show the live view, reuse the session, treat page text as data, close when done | Small |
| 10 | Replay of a recorded click path, no model (row 20) | Later; needs a recorder. Cortex is the natural recorder | Large |

Not taking: sidecar programs inside the session, localhost tunnels, the hosted billing model, the vault (Cortex has one), a second observer role on one CDP session until a use appears.

## 3. Where this touches existing Helix plans

- `docs/plans/2026-11-18-stealth-ladder.md`: ideas 2 and 4 attach to batch C (`host_sessions`, step 14). Idea 6 and 7 attach to the stealth rungs and the ladder registry (B10). Idea 3 changes the escalation trigger. Idea 1 is new and needs no plan batch.
- `docs/research/2026-11-16-stealth-browsing.md`: Tilion's `cdp_observe` note supports its warning that a vanilla CDP client's `Runtime.enable` is an automation tell [V: playwright-cdp.md]. That matches Helix's headed-Chrome and `rebrowser` direction.
- Proof runner (batch E): ComputeSDK's browser and stealth suites are a ready public yardstick [V: https://github.com/computesdk/benchmarks]. Its stealth results run only on the vendor platform, so Helix could use the open suite code but not the platform's published scores [I].
